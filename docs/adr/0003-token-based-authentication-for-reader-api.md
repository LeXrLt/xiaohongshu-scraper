# 0003. 阅读器 API 采用双 Token 换取与验证体系

- **日期**：2026-10-13
- **状态**：Accepted

---

## 背景与痛点 (Context)

阅读器后端 (`web/backend`) 暴露了笔记内容、商户知识库、以及包含登录凭据和爬虫配置的设置接口（`/api/settings`）。
此前 API 未设访问鉴权或仅依赖静态全局密码，存在严重安全隐患：
1. **静态密码长期暴露**：若每个 HTTP 请求均携带全局静态密钥，前端或外部调用者在网络抓包中极易泄露长效凭据。
2. **缺乏生命周期控制**：无状态长效密钥无法实施自动过期与灵活轮换。
3. **设置项敏感度高**：设置项中包含小红书账号 Cookie，一旦泄露可能导致账号封禁或数据被恶意操作。

---

## 决策内容 (Decision)

引入类似 OAuth 2.0 Client Credentials 的**双 Token 签名鉴权架构**：

1. **根密钥静态配置 (`API_AUTH_KEY`)**：
   - 规定必须为至少 32 字节高熵随机字符串，配置在服务端 `.env` 中。
   - 启动时强制校验密钥长度，不满足则拒绝启动服务。
2. **临时访问 Token 签发 (`POST /api/auth/token`)**：
   - 调用者在请求头传入 `X-API-Key: <API_AUTH_KEY>`。
   - 后端使用 `hmac.compare_digest` 防时序攻击校验密钥，成功后签发 HS256 JWT Token。
   - 载荷包含 `sub`、`iat`、`exp`、`iss` 和 `aud`，默认生命周期为 7200 秒（2 小时）。
3. **业务数据接口强制 Bearer 鉴权**：
   - 所有数据接口（`/api/notes`、`/api/merchants`、`/api/settings` 等）均挂载 `require_token` 依赖项，只认 Bearer JWT。
   - 根密钥无法直接用于请求数据接口。
4. **前端透明自动维护**：
   - 前端在内存中维护 Token 状态，快过期前（5分钟缓冲期）自动提前换取新 Token；多并发请求排队等待同一次刷新，保障用户无感。

---

## 影响与后果 (Consequences)

### 正面收益
- 传输过程中的 Bearer Token 具备时效性，即便被窃取也会在短时间内失效。
- 管理员仅需在 `.env` 中更换 `API_AUTH_KEY` 并重启，所有旧 Token 立即全网失效，具备即时吊销能力。
- 标准化 OpenAPI 契约，完美适配第三方系统与 MCP 客户端接入。

### 妥协与代价
- 客户端在首次发起数据请求前需多消耗一次 HTTP 往返换取 Token（通过内存缓存与连接复用削减至可忽略）。
